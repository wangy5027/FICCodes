# FICCodes｜论文代码与复现资料

本仓库集中整理团队已发表论文的代码、运行说明及相关资源，方便研究成果归档、共享与复现。

每篇论文由第一作者或第二作者指定一人负责提交，另一人协助核对。每篇论文只保留一个独立文件夹，后续修改在原文件夹内更新。

## 一、文件夹命名

每篇论文在仓库根目录下建立独立文件夹，统一命名为：

```text
上传人英文全名_论文简写_年份_期刊或会议缩写
```

例如：`YangWang_BoA-SQL_2026_EAAI`，表示上传人 Yang Wang、论文简称 BoA-SQL、发表年份 2026、期刊缩写 EAAI。

- 四项信息缺一不可，用下划线 `_` 分隔；这里的“+”表示信息组合，不作为实际文件名字符。
- 上传人必须使用本人完整英文姓名，按论文署名顺序书写，各部分首字母大写并去掉空格，例如 `Yang Wang` → `YangWang`。不能用 GitHub 用户名、中文名或姓名首字母代替。
- 论文简写优先使用论文中的方法或模型简称；没有明确简称时，由负责人确定简短英文名称。
- 年份以论文汇总表记录的发表年份为准。
- 期刊或会议使用通行英文缩写，例如 `EAAI`、`ACL`、`SIGMOD`；不确定时先确认，不自行编造。
- 四个字段内部只使用英文字母、数字或连字符 `-`；下划线只用作字段分隔，不使用空格、中文或其他符号。大小写确定后保持一致。
- 一篇论文只建一个目录，由第一作者或第二作者确定一名上传负责人。在该论文 README 中记录其英文全名和 GitHub 用户名；代为操作的 Agent 使用该负责人的信息。
- 创建目录前核对已有论文，避免同一论文因换账号、换上传人或改拼写而重复归档。遇到同名不同论文、负责人变更或已有目录不合规范，先联系维护者，不自行覆盖或改名。

### 修改范围：每次只允许修改自己的论文目录

**任何论文贡献者及其 Agent，只能在自己负责的一个论文文件夹内新增、修改、删除或移动文件，禁止改动该目录之外的任何文件。** 此规则同时适用于本地整理、Fork 内提交及最终 PR。

- 禁止修改其他人的论文目录，以及自己本次提交以外的其他论文目录。
- 禁止新增、修改或删除根目录 README、根目录 `.gitignore`、许可证、`.github/`、工作流和其他仓库级文件；不得在根目录创建个人说明、汇总表、PR 说明文件或临时脚本。
- 项目依赖、运行配置、`.gitignore` 和项目说明均放在自己的论文目录内，不能为了运行自己的项目修改公共配置。
- 禁止批量格式化整个仓库、全仓替换文本、移动他人文件、创建目录外副本，或通过符号链接绕过目录边界。目录内移动也不能跨越论文目录边界。
- 每篇论文使用独立分支和独立 PR，从主仓库最新 `main` 创建；后续修订继续使用该 PR 的分支。不要在包含其他论文未合并改动的分支上开始新提交。
- 只暂存自己的论文目录，禁止使用 `git add .`、`git add -A` 或 `git commit -a` 等可能纳入目录外改动的操作。
- 提交前检查全部暂存文件；发起或更新 PR 前检查相对主仓库的完整文件清单，新增、修改、删除和重命名涉及的路径必须全部位于自己的论文目录。发现越界改动应停止提交并查明原因，不覆盖他人的本地工作。
- 合并冲突只允许处理自己目录内的文件。涉及公共文件或他人目录时，停止并联系维护者；不得整批采用自己的版本覆盖主仓库内容。
- 仓库级规则由维护者在独立的仓库维护任务中处理，不属于论文上传任务。贡献者和 Agent 发现公共文件需要修改时，只报告建议，不自行修改。

维护者审核 PR 时应核对命名、负责人和全部文件路径；不符合范围要求的论文 PR 应先退回修改。本文是提交规则，不能单独构成 GitHub 的目录权限限制。

## 二、每篇论文必须提交什么

提交内容应让其他人在获得所需数据后，能够按照说明安装环境并运行论文代码。

| 必交内容 | 具体要求 |
| --- | --- |
| 论文说明 `README.md` | 论文全名、作者、发表年份、期刊或会议、论文链接、代码负责人及其 GitHub 用户名 |
| 源代码 | 论文主要方法及其所需的数据处理、训练、推理或评估代码；按研究实际提供 |
| 环境与依赖说明 | 编程语言及版本、关键框架版本、安装方法；提供适用的依赖文件，如 `requirements.txt` 或 `environment.yml` |
| 运行说明 | 按顺序给出数据准备、预处理、训练和评估的实际命令；按项目实际提供，并说明命令从哪个目录执行 |
| 数据获取说明 | 按下文要求提供数据下载链接、使用范围和放置路径 |

如果运行依赖预训练模型、分词器、检查点或其他外部资源，也必须说明其准确名称、版本、获取链接和本地放置位置。不要使用只在提交者电脑上存在的绝对路径。

如果论文没有配套代码，例如部分综述类论文，仍需建立论文文件夹并提交 `README.md`，说明论文信息及无代码的原因，不得以空文件夹代替。

## 三、数据集如何提供

### 1. 使用公开数据集

必须在论文文件夹的 `README.md` 中列出：

- 数据集名称及使用的版本。
- **数据集官方下载链接或官方获取页面。**
- 实际使用的子集、时间范围及训练集、验证集、测试集划分。
- 下载后的目录结构和本地放置位置。
- 必要的预处理步骤及对应命令。

需要注册、申请或同意使用条款的数据集，应说明获取条件。不要只写数据集名称，也不要只提供引用论文而不提供获取入口。

### 2. 使用自有数据集

**可以共享的自有数据必须提供百度网盘下载链接**；设置了提取码的，必须同时给出提取码。

同时说明：

- 数据内容、字段含义和文件格式。
- 数据版本、样本范围及数据划分。
- 下载、解压后的放置位置。
- 链接有效期；建议使用长期有效链接并维护其可用性。

自有数据须确认具备共享权限，涉及个人信息或敏感内容的应先完成必要处理。确实不能公开的数据，不得上传或通过公开网盘分享；应在说明中写明限制原因、可用的申请方式，以及缺失数据对运行的影响。有条件时提供可共享的示例数据。

### 3. 数据说明示例

```text
数据集名称：
数据来源：公开数据集 / 自有数据集
数据版本：
下载链接：
提取码：无则写“不需要”
获取条件：无则写“无”
本地放置路径：
数据划分：
```

公开数据集如需预处理，请另附步骤和命令。

## 四、什么可以上传，什么不能上传

| 类型 | 处理方式 |
| --- | --- |
| 源代码、配置文件、依赖文件、运行脚本 | 上传到论文文件夹 |
| README、必要的说明文档、小型结果表和示意图 | 可以上传到论文文件夹 |
| 可共享的小型示例数据 | 可以上传，并说明用途与来源 |
| 完整训练数据、较大数据集 | 提供下载链接，不直接提交到仓库 |
| 模型权重、训练检查点、大型实验输出 | 提供下载链接，不直接提交到仓库 |
| Python 虚拟环境、依赖安装目录、缓存、临时文件 | 不上传，例如 `.venv/`、`node_modules/`、`__pycache__/` |
| 大量训练日志、重复备份、与论文无关的文件 | 不上传 |
| 密码、API Key、访问令牌、私钥及含密钥的 `.env` | 禁止上传；可以提供不含真实凭据的 `.env.example` |
| 未经授权的数据、未处理的隐私数据、无权公开的第三方文件 | 禁止上传 |
| 整个项目的 ZIP、RAR 等压缩包 | 不作为代码提交方式，请展开为可浏览的文件和目录 |
| 本地 Git 历史目录 `.git/` | 不上传，不把论文目录建成嵌套仓库或子模块 |

本仓库为公开仓库，提交前请检查文件内容及代码中硬编码的路径、账号和凭据。建议在论文文件夹内添加 `.gitignore`，排除数据、权重、环境和缓存等不应提交的文件。

## 五、通过网页提交：Fork → 上传 → Pull Request

### 第一步：创建自己的仓库副本

1. 登录自己的 GitHub 账号。
2. 打开主仓库：<https://github.com/wangy5027/FICCodes>。
3. 点击右上角 **Fork**，再点击 **Create fork**。

这会在你的账号下建立仓库副本。后续代码先提交到自己的副本，再申请合并到主仓库。已有副本时，先通过 **Sync fork** 同步主仓库更新。

### 第二步：创建本次提交的分支

在自己的仓库副本中，点击文件列表上方的分支选择框，以更新后的默认分支为基础创建新分支，例如 `add/YangWang_BoA-SQL_2026_EAAI`。

每篇论文必须使用独立分支、提交独立 PR。

### 第三步：上传论文文件夹

1. 在电脑上整理好 `上传人英文全名_论文简写_年份_期刊或会议缩写` 文件夹。
2. 确认网页当前位于自己的仓库副本和本次提交的分支。
3. 点击 **Add file → Upload files**。
4. 将整个论文文件夹拖入上传区域。
5. 检查文件路径，确保代码位于论文文件夹内，而不是散落在仓库根目录。
6. 填写提交说明，例如 `Add YangWang_BoA-SQL_2026_EAAI code and documentation`。
7. 点击 **Commit changes** 完成保存。

网页上传单个文件不能超过 25 MiB，一次最多上传 100 个文件。文件较多时可分批上传，全部完成后再提交 PR；也可使用 GitHub Desktop、Git 或下文的 Agent 流程。

### 第四步：向主仓库发起 PR

上传完成后，在自己的副本中点击 **Contribute → Open pull request**；也可以通过 **Pull requests → New pull request** 创建申请。

检查目标：

```text
目标仓库（base repository）：wangy5027/FICCodes
目标分支（base）：main
来源仓库（head repository）：你自己的仓库副本
来源分支（compare）：本次提交的分支
```

PR 标题统一写为 `提交：上传人英文全名_论文简写_年份_期刊或会议缩写`。

PR 说明应包含：

```text
论文全名：
论文文件夹：
提交负责人：
GitHub 用户名：
本次提交内容：
数据下载链接所在位置：
已执行的检查：如尚未运行，请如实说明
尚未解决的问题：无则写“无”
```

创建 PR 前核对完整变更文件列表，确认所有路径均在自己的论文目录内，包括删除和重命名的旧路径。点击 **Create pull request** 后，将 PR 链接交给仓库维护者。

**只上传到自己的副本不算完成，必须向主仓库发起 PR。**

### 第五步：修改和收录

维护者检查后，可能要求补充文件或修改说明。请继续在原 PR 对应的分支上提交修改，PR 会自动更新，无须重复创建申请。

维护者合并 PR 后，该论文文件夹才会正式进入主仓库。合并表示完成归档收录，不自动代表所有实验结果均已由维护者复现验证。

## 六、通过命令行提交：Fork → 分支 → Pull Request

以下示例使用 PowerShell、Git 和 GitHub CLI（`gh`）。Git 负责代码操作，`gh` 负责 GitHub 授权、Fork 和 PR。先安装这两个工具，首次执行 `gh auth login` 完成本人授权，再用 `gh api user --jq .login` 核对账号。提交署名与推送认证是两项独立设置，均应对应本人。

### 1. 准备个人副本和分支

已有 Fork 时复用它；已有本地克隆时进入该目录，跳过 Fork、克隆和添加已有远程的步骤。开始前保证工作区干净，不覆盖已有工作。

```powershell
gh repo fork wangy5027/FICCodes --clone=false
$account = gh api user --jq .login
git clone "https://github.com/$account/FICCodes.git"
Set-Location FICCodes
git remote add upstream https://github.com/wangy5027/FICCodes.git
git fetch upstream

# 替换为自己的论文目录和一个尚未使用的分支名
$paper = "YangWang_BoA-SQL_2026_EAAI"
$branch = "submit/$paper"
git switch -c $branch upstream/main
```

按新命名规则准备自己的目录，只在该目录内整理代码和说明。示例中的 YangWang 目录归其负责人所有，其他上传人应替换为自己的真实信息。所有后续命令均在仓库根目录执行；任一命令失败时停止，处理后再继续。

### 2. 检查范围、提交并推送

```powershell
git status --short
git diff --check
git diff -- "$paper/"
git add -- "$paper/"

# 检查所有暂存路径；禁用重命名检测以同时列出旧路径和新路径
$outside = @(git -c core.quotepath=false diff --cached --name-only --no-renames | Where-Object { -not $_.StartsWith("$paper/", [System.StringComparison]::Ordinal) })
if ($outside.Count -gt 0) { throw "暂存区有论文目录之外的变更，停止提交：$outside" }
git diff --cached --check
git diff --cached --stat
git diff --cached
git commit -m "Update $paper"

# 检查整个分支，不能只检查最后一次提交
git fetch upstream
$outside = @(git -c core.quotepath=false diff --name-only --no-renames upstream/main...HEAD | Where-Object { -not $_.StartsWith("$paper/", [System.StringComparison]::Ordinal) })
if ($outside.Count -gt 0) { throw "PR 包含论文目录之外的变更，停止推送：$outside" }
git diff --check upstream/main...HEAD
git diff --stat upstream/main...HEAD
git diff --name-status --no-renames upstream/main...HEAD
git push -u origin $branch
```

上述范围检查帮助发现路径越界，仍须人工或 Agent 审阅完整差异、负责人归属及敏感内容。未跟踪文件不会出现在 `git diff` 中，因此还须核对 `git status --short`，不得把目录外未跟踪文件加入提交。

### 3. 创建和更新 PR

按第五节的 PR 说明模板，在系统临时目录准备说明文件，不要在仓库根目录创建该文件。下面会打印临时文件路径；填写真实信息后再执行创建 PR 的命令，不要将空文件或未替换模板作为说明提交。

```powershell
$prBody = New-TemporaryFile
$prBody.FullName
# 将完整 PR 说明写入上面显示的文件后，继续执行
$account = gh api user --jq .login
gh pr create --repo wangy5027/FICCodes --base main --head "${account}:$branch" --title "提交：$paper" --body-file $prBody.FullName
```

后续修订仅修改自己的论文目录，重复范围检查、提交并推送到同一分支，原 PR 会自动更新，无须重复创建。每次推送前重新检查整个分支。主仓库有更新时先获取最新状态；若需合并或变基，只解决自己目录内的冲突，目录外冲突交由维护者处理。由维护者审核和合并 PR，贡献者及 Agent 不替维护者合并。

## 八、提交前自查

- [ ] 文件夹名称符合 `上传人英文全名_论文简写_年份_期刊或会议缩写`。

- [ ] 论文 README 信息完整。
- [ ] 源代码和依赖说明齐全。
- [ ] 安装、数据获取和运行命令清楚。
- [ ] 公开数据集已提供官方获取链接及必要的预处理说明。

- [ ] 所需模型及其他外部资源有明确获取方式。
